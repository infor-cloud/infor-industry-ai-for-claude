# Settings: found at run time, never stored

Shared reference. The plugin carries no customer values. Every setting is read from M3 at run time, or asked of the user
when a step needs it.

- **Look it up first** with the tool named below. Ask only when M3 can't give it.
- **Ask once, when the step that needs it comes up**, in one short question that says why it is needed and who usually
  knows (often the M3 administrator). Don't ask up front for things the work may never need.
- **Keep every answer for the rest of the conversation**; never ask twice. Show the values you used in the answer's scope
  line. Don't claim they are saved anywhere.
- If the conversation is in a Claude Project whose instructions give a value, use it and don't ask.
- **Never guess.** Never take a value from an example, from another customer's data, or from an earlier conversation.
- The user can change any value in a prompt ("another warehouse, 21 days"); the prompt wins.

**In the rep dashboard** (`assets/rep-dashboard.html`) the settings are the **focus order type** (the order type to follow closely) and **Days back** (the look-back for open orders, default 90 days, see the table below): the user enters it once, in its Settings box or from the notice at the top of the Focus Orders tab, and the box takes 3 characters. The allocation origin (1) and the message type (001) are M3's usual codes, built in and not shown. The page has no link to the credit controller. The focus order type is **remembered for the person**, in a private row of the page's own database (`data/users/<id>/settings`, readable only by that person), so it is said once. The plugin itself ships no value, and the page uses no browser storage. A shared row `config/settings` can hold a default for people who have none of their own: whoever publishes the page can set it once, and a person's own choice always wins. If the page cannot store anything (no database, or the person is not signed in), it asks again at every visit and says so. **Clear** removes the private row. The type of a donor order is read from that order's header.

### What the rep dashboard assumes about a tenant

The page carries none of the demo tenant's order types, items, warehouses, customers or links: it reads configured data from M3 at run time. These are the places where it still **assumes** how M3 is set up. If a tenant differs, M3 refuses the write or the page shows a wrong label. The two built-in codes are sent without being shown, so these assumptions are the thing to check.

| Assumption | Where it is used | Holds when | If it does not hold |
|---|---|---|---|
| Allocation origin **1** means manual allocation (built in, not shown) | Take stock and allocate pop-ups | It is an M3 system value. Tested in one tenant only; the tool gives no list of values | M3 refuses the allocation; the page says so and nothing changes |
| Message type **001** (manually created message) (built in, not shown) | The reminder to the warehouse | The tenant kept M3's standard entry in its message type setup (CRS424) | M3 refuses; the page says "Nothing was sent" |
| Stock transaction type **CustomerOrderIssue** | Allocation and take stock | Always: it is a fixed M3 list | Not applicable |
| Customer order stop codes **1 to 8** are credit stops: 1 to 6 set by M3's credit check, 7 and 8 set by hand. Credit details are read for codes 1 to 3 | The "Escalate to credit" filter, the credit box and the key measures | The tenant has not given these codes another meaning | A stop that is not a credit stop would be shown as one and handed to the credit controller. Check the tenant's stop code setup first |
| Only item relations of **type 1, 2, 3 or 4** (1 complete replacement, 2 replacement after the balance is used, 3 conditional interchangeability, 4 full interchangeability) are alternative items for the rep, read from the line's item to the related item. The planner's material swap uses **types 3, 4 and 5** (5 is product alternative material) | The alternative item option, in swap and in Create CO (rep) and in the planner's swap | The tenant records its alternatives that way | No alternative is offered for relations of another type, for example an accessory (type 7) or the Web Shop types 7 to 9 |
| Order line status **33** means allocated | Finding the orders that can give stock | Standard M3 status | No donor is found |
| Changing the confirmed date applies **at once**, on every line, when only the order and the date are sent (no update mode) | The "Change confirmed date" action | The customer order types in use have the field "Confirmed delivery date" **open for change**: in OIS014 (field selection of the customer order type) its entries are blanked out, which opens the field for change in OIS101/I (Customer Order. Open Line), and then the API change goes through too. Reported by the tenant's M3 consultants; not read by us. M3 gives no reason when a date does not change, so the page only points to directions, none of them certain: a field closed for change in OIS101/I, connected settings such as the delivery route and its departures, an availability (ATP) check. The API may say more in a later version | M3 accepts the call **without an error** and the date stays. The page reads every line back, says which line shows which date after up to 8 seconds, and prepares no customer update |
| A picking list exists when the **quantity on picking lists** (`PickingListQuantityBasicUom` on the delivery lines of an order line) covers the ordered quantity of every line | The "Picking" step and the "Next:" line of a stock order in the Focus Orders tab | The delivery lines carry that quantity, as they do in the tested tenant | If M3 gives an error or the tool is missing, picking is shown as not known (never claimed) and the open circle stays on "Picking" |
| Purchase order **status numbers** (M3's fixed list): under 20 is not sent yet, 11 to 14 is stopped, 20 to 30 is sent, 31 to 35 is confirmed by the supplier, 40 and 45 is on the way, 50 and up is received | The step of a purchase order and the "Next:" line in the Focus Orders tab | These are M3's own purchase order statuses, read from the tool definition on 2026-11-03: the same in every tenant, not a customer setting | A status number that is missing is shown as "Waiting for the buyer", never as a later step; a status outside the list is placed by its number range |
| The M3 connector is found by the **M3 tools it offers** (a connector whose tools include `OIS100MI_GetLine`), not by its name | Connecting, at the start of the page | The viewer's connector lists its tools, and the connector's name in the page's capabilities is the one the viewer has | With one M3 connector it is used; with several, the one this page is allowed to use is chosen (one that is not in its manifest is refused before anything runs); if none offers the M3 tools, nothing is sent and the page says it is not connected |
| Open orders are **left out of the lists** when their requested delivery date (on the order header) is older than the look-back, **default 90 days** (the setting "Days back"; the same default as the planner's MO lookback). Orders due today or later are never left out | The Needs Action, On Track and Focus Orders lists, the key measures, and the text view in chat | The header's requested date says when the customer wants the goods; the date is compared by the page itself because a date filter in the search can silently return nothing | An old open order that still matters is not listed until the look-back is made longer. Every list says "Looking back N days ... N older open orders left out", so the rule and the number of orders left out are always visible |
| The focus order type is **remembered** in the person's private row `data/users/<id>/settings` (and an optional default in `config/settings`) | The Settings box and the start of the page | The platform's `db` and `user` capabilities are declared and available to the viewer, and the person is signed in | The page asks again at every visit and says "Kept for this visit only"; it never waits more than 2.5 seconds for the saved value |
| Take stock: a donor must be due **more than 3 days** from today (built in as one number, `PROTECT_DAYS`) and **later** than the line that needs the stock; the order type of neither plays a part | Take stock in the options and in the pop-up, checked again right before the write | A business rule, the same in every tenant. A donor's date is the plan's date for its line, which is the confirmed date | An order due sooner, or already late, is never asked to give up its stock; the row says how many were left out and why |
| An order that is short of **free** stock, while the plan balance for its line is not negative, is **"Stock held by other orders"** | The status, the options (take stock first) and the "Next:" line in the Focus Orders tab | M3's plan counts all stock on hand for every demand in date order, also stock that is allocated to other orders | If the plan cannot be read, the order is a shortfall with "the plan could not be read" and no donor is offered |

**Check these in a new tenant, with a new user, before a customer demo** (about ten minutes): allocate one line (origin), send one reminder (message type), open a credit-stopped order (stop codes), and open an item that has an alternative (relation type), and change the confirmed date of a test order of each order type in use and read every line back (order type setup). Anything that differs is a setting of that tenant, not a fault of the page: change the tenant's setup or tell the owner of this file.
